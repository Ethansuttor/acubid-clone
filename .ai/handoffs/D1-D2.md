## Persistence origin decision and evidence

Decision: **option (b)**. The renderer loads `voltline://app/…`, a privileged
scheme registered as standard + secure + fetch-capable. The main process
proxies it to this launch's loopback Next.js server, which binds an
OS-assigned free port. IndexedDB, Web Locks and localStorage are keyed by
`voltline://app`, which contains no port.

Why not (a), a fixed port: another program (or another Voltline profile) can
hold the port, and any change of port silently changes the origin so existing
workspaces look empty. (b) removes the port from the origin entirely and lets
the OS choose a free one, so port collisions cannot block startup or change
identity. Costs of (b): every request passes through the main process; the
proxy does not carry WebSocket upgrades (unused by the production server); and
`voltline://app` must never change between releases. The C1 bridge, status
pages and navigation policy all key off that origin.

Evidence (test `keeps the workspace across a restart on a different server
port`): launch 1 with `--voltline-server-port=3161`, log in, create a project,
wait for saves to settle, quit; launch 2 on the same data directory with
`--voltline-server-port=3162`; still signed in and the project is listed.
`location.origin` is `voltline://app`, `isSecureContext` is true,
`navigator.locks` and `indexedDB` are present, and a POST to `/api/autocount`
through the proxy returns 401 (the production guard), so request bodies cross
the proxy. Not established: PDF.js worker and detection worker under this
origin (not run), and durability beyond "IndexedDB survives a graceful quit".
D2 stays an explicitly limited IndexedDB preview; it does not establish SQLite
durability, and browser data at `http://localhost:3000` is a different origin
that Electron cannot read (use portable backup/restore).

Server hardening (implemented; the end-to-end handshake is live-verified, the
proxy header rules and child environment are unit-tested, but the entry
script's 403-without-token behavior has no test of its own): per-launch UUID and 32-byte token sent
over the utility process's private message port (never argv/env); the server
entry wraps the first `http.createServer`, forces `127.0.0.1` and the chosen
port, rejects any request without the token (403) and stamps every response
with the launch id; main accepts readiness only from a 200 on `/login` that
carries that id, within a bounded deadline (default 60 s,
`--voltline-startup-timeout-ms`). The child gets an allowlisted environment
(no proxy variables, no provider keys, no `NODE_OPTIONS`).

Excluded on purpose: `sharp` and `@img/*` (next/image optimisation, unused,
platform-specific native code). The stage fails if the tree contains `.env*`,
`.git`, Next build cache, test/eval output, PDFs outside dependencies, or
`*.tsbuildinfo`, and it refuses symlinks that leave the build. Worker assets
present at stage time: `pdf.worker.min.3rhk85vwt0vjb.mjs` and
`turbopack-worker-2ru9m5gbh1na6.js` (the detector's worker bootstrap).
All paths derive from `app.getAppPath()/../server`, never the working
directory. `.next/` is shared with the browser build, so run
`npm run desktop:build` again after `npm run build` (stage refuses a
non-standalone `.next`).

## Startup failure behavior (implemented; not exercised by a test)

A status window (`voltline://shell/`, its own origin, its own preload with a
four-action allowlist and no C1 bridge) shows "Starting Voltline…", then on
failure the reason and the last server output plus the log path
(`<data dir>/logs/voltline-desktop.log`, rotated at 1 MB), with "Try again" and
"Quit". Failure kinds: payload missing, spawn failed, exited during startup,
timeout, handshake mismatch (wrong id, non-loopback address, wrong port). An
unexpected server exit after startup opens a notice window with "Restart local
server"; while it is down, `voltline://app/*` answers 503 rather than hanging.
A renderer crash offers "Reload window". An unwritable data folder is reported
instead of falling back to another profile. A malformed `--voltline-*` switch
is an error, never a default.

- Renderer configuration: `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false` verified live on the workspace window. `webviewTag: false`, denied `window.open` and cancelled `will-attach-webview` are configured in code but not exercised by a test.
- OS sandbox: **verified on Linux, running as the non-root user `voltdesk`, without `--no-sandbox`**: every renderer process reports `Seccomp: 2` and `NoNewPrivs: 1` (test `renderers run under the OS sandbox`). Chromium refuses to run as root; the launcher throws when root unless `VOLTLINE_E2E_NO_SANDBOX=1`, in which case it adds `--no-sandbox`, skips that assertion and the OS sandbox is **not verified**. `--no-sandbox` is never passed by production code.
- The staged runtime is a plain copy of `node_modules/electron/dist`, so its default fuses are on and Playwright's `_electron` can attach (it needs the Node CLI inspect fuse). D4 must keep that available for a test build.
- Windows sandbox and integrity levels: not verified.
