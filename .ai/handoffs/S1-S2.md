## Design record

### Driver and runtime
Built-in `node:sqlite` (`DatabaseSync`). Verified in this container: Electron
44.4.5 in `ELECTRON_RUN_AS_NODE=1` mode reports Node 24.21.0, SQLite 3.53.4,
`node:sqlite.backup` present. The API is **synchronous**: a write blocked by
another process waits up to the busy timeout (default 5000 ms) on the calling
thread. I1 should host the store in a utility process or worker thread, not the
Electron main UI thread.

### Pragmas (recorded, and verified at every open)
- `journal_mode = WAL` (open fails with `unavailable` if not granted)
- `synchronous = FULL` (verified; open fails otherwise). Commits are fsynced
  before the call resolves. Trade-off chosen: latency over throughput; nothing
  was traded for speed.
- `foreign_keys = ON` (set, then read back; open fails otherwise; also passed
  as the `enableForeignKeyConstraints` open option)
- `busy_timeout = 5000` (option `busyTimeoutMs`)
- `enableDefensive(true)`
- `application_id = 0x566f6c74` ("Volt"), `user_version = 1`. A file with a
  different application id, or with tables and no version, is refused
  (`integrity`) unmodified. A newer `user_version` is refused (`unavailable`,
  "saved by a newer version") unmodified.

### Schema mapping (all 11 entities + `outbox` + `plan_files`)
Derived from `src/lib/types.ts`, all four Postgres migrations, and the columns
the browser client adds itself. All domain tables are `STRICT`.

| Logical type | SQLite | Notes |
| --- | --- | --- |
| id, text, `user_id`, FK ids | `TEXT` | `id` is `UNIQUE NOT NULL CHECK(length>0)`; rowid alias `_seq` preserves insertion order |
| timestamps | `TEXT` ISO-8601 | validated with `Date.parse`; returned as the same string |
| enums (`tool`, `kind`, `source`, `status`, `detection_review`, `category`) | `TEXT` + `CHECK IN (...)` | also validated in the codec |
| numbers (`numeric`) | column type `ANY` + `CHECK(typeof IN integer/real/null)` | `ANY` keeps the IEEE double bit for bit, including `-0`; REAL affinity does not. NaN/Infinity/strings rejected |
| ints (`page_count`, `sort_order`, `revision`, `warning_count`) | `ANY` + typeof + `= round()` CHECK | safe integers only |
| booleans (`ohp_applies`, `taxable`) | `INTEGER` 0/1 + `CHECK` | mapped back to `true/false` |
| json (`calibration`, `geometry`, `payload`) | `TEXT` + `CHECK(json_valid)` | plain objects only; `-0` preserved via `JSON.rawJSON`; non-finite, undefined array items, cycles, non-plain objects rejected |
| absent vs null | `_absent` JSON list | a column never supplied stays absent on read; explicit `null` stays `null` |
| unknown fields | `_extra` JSON | preserved verbatim, not dropped |

Domain rules carried over: `bond_pct` in [0,100), `typical_multiplier > 0`,
`revision > 0`, `warning_count >= 0`, `UNIQUE(document_id, page_number)`,
`UNIQUE(project_id, revision)`, `ON DELETE CASCADE` for every parent link that
the browser cascade set covers.

Deliberate differences from Postgres, recorded for review:
- Presence is not enforced except for `id`: rows written before a column
  existed must migrate unchanged; readiness belongs to preflight.
- `layers.item_id` / `assembly_id` are **not** foreign keys. The browser keeps
  a dangling link after a catalog delete, which `extendEstimate` reports as
  missing-item/assembly. Postgres `ON DELETE SET NULL` would turn that into
  "unlinked". Browser behavior preserved (and asserted in the contract suite).
- No users table; `user_id` is plain text.

Indexes: `takeoffs` (project, sheet, layer), `sheets(project)`,
`layers(project)`, `documents(project)`, `documents(storage_path)`,
`assembly_items` (assembly, item), `direct_costs(project)`,
`proposal_entries(project)`, plan_files(sha256), plus the unique keys.

### Same-transaction outbox
Every mutation runs `BEGIN IMMEDIATE ... COMMIT`; the row writes, the
project-`updated_at` touch, and exactly one `outbox` row (append-only,
`AUTOINCREMENT` sequence, `synced_at` null) commit together or not at all. The
promise resolves after COMMIT. There is no other journal. Tests: injected
failure before COMMIT leaves rows, project touch and outbox untouched; SIGKILL
tests assert `count(outbox) == 1 + committed batches`.

### Plan files
```
<dataDir>/voltline.db (+ -wal, -shm)
<dataDir>/workspace.lock
<dataDir>/plans/staging/<uuid>.part          being written; never referenced
<dataDir>/plans/objects/<aa>/<sha256>        published, immutable
```
`plan_files(storage_path PK, sha256, size, content_type, created_at, removed_at)`
maps the logical path (unchanged, so historical `storage_path` values in frozen
snapshots stay valid) to the hash. Upload: stage (exclusive create, fsync) ->
re-read and verify SHA-256/size -> rename into `objects/` + fsync directories ->
only then commit the mapping row. A `documents` insert/update is refused by a
trigger unless a live mapping exists. A crash can leave a staging file or an
unreferenced object; it cannot leave a committed reference to missing bytes.
Paths are only database keys, never joined into file-system paths (hostile
names tested). A path is never rebound to different bytes, live or retired
(`conflict`). Removing a path (or its document) **retires the mapping and
never deletes bytes**; `planFileInventory()` reports live/retired paths,
document and frozen-snapshot references, unreferenced objects, missing
objects and staging leftovers. Garbage collection is deliberately not
implemented (needs the S3 backup manifests and a grace period). Reads verify
size and SHA-256; a mismatch or missing object is `integrity`, and
`exportBundle` fails rather than carrying damaged bytes.

### Lock mechanism
`withExclusiveWorkspace` and `acquireEditingLease()` (extension, see below)
take `BEGIN EXCLUSIVE` on a separate, otherwise unused SQLite file,
`workspace.lock`, with busy timeout 0, and hold that transaction open. A second
process or connection gets SQLITE_BUSY immediately -> `occupied`. The OS drops
the lock when the holder exits or is killed: no PID file, no stale-lock
cleanup (verified with SIGKILL). Like SQLite itself it requires a local file
system; network/cloud-sync folders are unsupported. Windows locking semantics
(`LockFileEx`) are SQLite's documented behavior but were not exercised here.

### Migrations
`PRAGMA user_version`, ordered list `MIGRATIONS`, applied inside one
`BEGIN IMMEDIATE` (re-checked inside the lock so two processes cannot both
migrate). A shipped migration's SQL is a frozen literal, never regenerated
from the spec; `verifySchema` fails closed if the spec and disk disagree. The
option `migrations` is a test seam (tested: upgrade keeps data; a failing
upgrade rolls back whole and the last good database reopens).

## Contract-change requests (the frozen C1 port was not edited)

1. **Add `upsert(table, rows)` to `WorkspaceStoragePort`.** `src/store/workspace.ts`
   calls `.upsert()` for takeoffs, items, assemblies, direct_costs and
   proposal_entries. The SQLite store implements it as an extra method
   (`SqliteWorkspaceStore.upsert`, browser-store semantics: insert or merge by
   id); the port and the browser/fake adapters do not have it, so the contract
   suite does not cover it. I1 cannot route those call sites through the port
   without this.
2. **Editing lease.** `acquireEditingLease()` (returns `{ release() }`) is an
   extension on the SQLite store, the desktop equivalent of WorkspaceAccess's
   Web Lock. Consider adding it to the port (or a capability-gated companion)
   so the shell can hold the workspace while a project is open.
3. **Optional single-row read.** `single()` is expressible as `select` by id (exact-one
   is asserted in the contract suite); no change strictly needed.
4. **Extensions worth exposing to the shell (no port change needed):**
   `backupDatabaseTo(absolutePath)`, `verifyIntegrity()`, `planFileInventory()`,
   `diagnostics()`, `close()`. S3 will need `backupDatabaseTo` plus PDF pinning.
5. `PlatformCapabilities` for the desktop store is `kind: "desktop"`,
   `recordStore: "sqlite"`, `fileStore: "filesystem"`,
   `exclusiveWorkspaceLock: true`, `folderMirror: false`, `aiTransport:
   "unavailable"`, `managedCredentials: false`. I1 must compose the final
   runtime capabilities.

## Stricter-than-browser behavior (intentional, documented)

These hold on SQLite and are tested there. The browser adapter is looser; I did
**not** add tests recording the browser's looser behavior (see gaps).
- Unknown table, wrong value types, non-finite numbers, out-of-range
  `bond_pct`/`typical_multiplier`, bad enums, lone surrogates, non-object JSON
  -> `invalid-input`, nothing written.
- Orphan foreign keys (e.g. a layer for a missing project) -> `invalid-input`.
- Duplicate `(project_id, revision)` -> `conflict`. Omitted `revision` is
  allocated as max+1 per project inside the transaction. (The app currently
  computes the revision in JS; the browser store has no uniqueness constraint.)
- `bid_snapshots` rows are frozen: `update`/`upsert` of an existing snapshot ->
  `conflict`. Deleting the project still removes them (as the browser does).
- A document needs its plan bytes uploaded first (the app already does this).
- Duplicate `(document_id, page_number)` sheets -> `conflict`.
- A logical plan path cannot be rebound to different bytes.
- Retiring a path that a document still uses -> `conflict`.

## Compatibility / migration effects

No browser data or format changed. `exportBundle` produces the existing
`voltline-recovery` snapshot (schema_version 1) so `encodeBackup/decodeBackup`
and `validateBackupSnapshot` work unchanged; the S1 contract test round-trips
a SQLite export through the real `.voltline.json` codec into a second SQLite
store. Restore additionally checks relations the SQLite schema enforces
(assembly components' parents, sheet-page and snapshot-revision uniqueness)
before any write. The browser -> desktop migration (S3) is not implemented.

## Remaining failures, gaps and missing inputs (be skeptical of these)

- **No performance baseline** (S1.5) and no Electron proof script were delivered.
  Any latency claim in other documents cannot cite this task.
  Expected cost only: SQLite writes are row-level (a test asserts a single
  edit in a >2 MB workspace grows the WAL by <256 KB); the browser adapter
  rewrites the whole state per mutation. That is a design observation, not a
  measurement.
- Contract gaps: `upsert` not covered (not in the port); no case for an export
  taken while writes are in flight; browser looser behavior not pinned by tests.
- Real IndexedDB in a browser engine: not run. Windows: not run. Packaged
  Electron: not run. Power loss, disk full, read-only volume, permission
  failures (container runs as root, so permission tests would be meaningless):
  not tested; the SIGKILL tests prove process-death behavior only. `synchronous
  = FULL` is the chosen setting, honored only as far as the OS and disk honor
  fsync.
- The store is single-process serialized (an in-process queue) plus SQLite's
  cross-process write lock; a very large `exportBundle` holds the queue while
  it reads PDFs.
- Restore deletes any `plan_files` mappings present in an otherwise empty
  workspace before installing the backup's (bytes stay on disk). This matches
  the browser's `files.clear()` on restore.
- A database upgrade does not take a pre-upgrade backup; S3 should do so
  before calling `open` (or a `beforeMigration` hook can be added).
- `health().writable` reflects the last failed write and clears on the next
  successful one; the app-level sticky `saveError` (invariant 10) remains the
  workspace store's job.
